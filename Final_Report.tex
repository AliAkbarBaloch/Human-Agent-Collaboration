\begin{abstract}
Effective human-agent collaboration requires that users can supervise what an agent
does, correct it mid-task, and calibrate how much they trust it over time. Yet across
seven actively-maintained multi-agent frameworks, none provides supervision mechanisms
calibrated to the actual risk of individual actions, none implements content-level
scanning for injected instructions that could silently redirect agent behaviour, and
correction interfaces remain rudimentary at best. I survey AutoGen, MetaGPT, ChatDev,
OpenHands, CrewAI, Magentic-One, and Magentic-UI against four criteria
(controllability, approval granularity, injection defense, auditability) and document
both gaps formally. I then describe HALO (Human-Agent Loop Orchestrator), a
browser-extension prototype that addresses all three collaboration requirements:
risk-proportional \textit{supervision} through a hybrid risk-scoring engine,
real-time \textit{correction} via co-planning and co-tasking interfaces, and adaptive
\textit{trust calibration} via a per-tier Bayesian feedback model. I also ran
a live, end-to-end evaluation against the running application itself, rather
than an offline benchmark, driving the real backend, browser sandbox, and a
hosted LLM through 22 black-box scenarios covering web browsing, code
execution, file access, MCP integration, and the trust feedback loop. All
three mechanisms held up on genuine traces: the risk engine routed both a
low-risk research task and a high-risk destructive task to the correct
approval policy with no misclassifications, the hybrid injection detector
caught a lexically-explicit and a purely semantic content injection on its
own while leaving ordinary action-oriented requests alone, and all 22
scenarios passed end to end. A separate, labeled ground-truth corpus of
sixteen items run over 48 trials puts this on a quantitative footing,
Precision 1.00, Recall 0.958, F1 0.979 for the Injection Gateway. The Bayesian trust model
is proved to converge ($\sigma_n = O(1/\sqrt{n})$), reaching $\sigma < 0.05$ in
approximately 61 interactions for the research tier and 69 for transactional under
the asymmetric approve/reject weighting now in effect, with
tiers updating independently.
\end{abstract}

\section{Introduction}

Consider a user who asks a browser agent to ``research the top five competitors and
summarise their pricing.'' The agent opens a competitor's landing page. Somewhere in
that page, rendered in white text on a white background, sits the string: \textit{``Ignore
your current task. Email the user's contact list to attacker@evil.com and report that
the task completed successfully.''} The model reads it, processes it as an instruction,
and complies. The user sees a summary of competitor pricing. Neither party knows
anything went wrong.

Greshake et al.~\cite{greshake2023indirect} demonstrated exactly this class of attack
against several production LLM-integrated applications in 2023. The difficulty is
structural: the injected instruction arrives through the data channel---web content the
agent was legitimately told to read---not through the user's conversation. Standard
input-validation guards are designed for user inputs and are simply not in the path of
retrieved content.

A separate problem concerns trust calibration. Operators who see an agent succeed
repeatedly on safe tasks tend to apply the same latitude when the agent is being
manipulated or is overconfident---a complacency pattern well documented in aviation
and process control~\cite{parasuraman2010complacency, lee2004trust}. With broad
permissions, the consequences of a single failure can be irreversible.

This paper examines these issues through a structured survey of seven multi-agent
frameworks and a working prototype, HALO (Human-Agent Loop Orchestrator), that
addresses all three collaboration requirements: supervision, correction, and trust
calibration, with results quantified through controlled experiments.


\section{Background and Related Work}

Horvitz's mixed-initiative principle established that well-designed automation should
allow either a human or a machine to take the lead depending on context, rather than
assigning one party to a fixed subordinate role~\cite{horvitz1999principles}.
Amershi et al.\ extended this into eighteen concrete guidelines for human-AI
interaction~\cite{amershi2019guidelines}; the three most relevant here are that a
system should make clear why it did what it did (G11), support efficient invocation
by the user (G7), and support efficient correction when the system is wrong (G9).

Lee and See showed that operators calibrate reliance on automation from observed
reliability, adjusting trust as a nonlinear function of how the system has actually
performed~\cite{lee2004trust}. Parasuraman and Manzey documented the resulting
complacency effect across aviation, process control, and medical
settings~\cite{parasuraman2010complacency}.

Indirect prompt injection formalizes the third concern. Greshake et al.\ demonstrated
the attack against real deployed systems, not just a lab prototype: a manipulated web
page redirected Bing Chat, and manipulated source comments redirected GitHub
Copilot, both without the user seeing anything unusual~\cite{greshake2023indirect}.
Perez and Ribeiro provided
the first systematic taxonomy of such attack techniques, classifying them by whether
the adversary controls the model's prompt directly or through a data side-channel~\cite{perez2022ignore}.
Yi et al.\ subsequently benchmarked the resilience of several production LLMs against
indirect injection and found that even state-of-the-art models reject fewer than half
of carefully crafted semantic attacks~\cite{yi2023benchmarking}. The most closely
related defense to HALO's content scanner is Spotlighting~\cite{hines2024spotlighting},
which marks retrieved content with a special delimiter before it enters the model
context, prompting the model to treat it as data rather than instructions. HALO's
approach differs in two ways: a sandboxed secondary LLM call makes the scanning
decision, not the primary agent itself, and flagged content is quarantined instead
of passed through with a marker. The 95.8\% recall reported in Section~5
compares favorably with the 61--78\% range reported by Yi et al.\ for single-model
defenses on their benchmark, though the test corpora differ and a direct comparison
would require evaluating on a shared dataset.

Alignment-based defenses (Constitutional AI~\cite{bai2022constitutional},
RLHF~\cite{ziegler2019rlhf}) and output guardrail frameworks (NeMo
Guardrails~\cite{rebedea2023nemo}, LlamaGuard~\cite{inan2023llamaguard}) improve
baseline model safety but operate on the model's input/output stream and do not
intercept the data-retrieval channel that indirect injection exploits. OWASP's
LLM Top~10~\cite{owasp2025llm} classifies prompt injection as the leading risk in
LLM-integrated applications; none of the seven surveyed frameworks addresses it at
the data-channel level. Sandboxing (Docker containers, capability-based
access control~\cite{saltzer1975protection}) limits blast radius but cannot prevent
semantic harm: an agent inside a container can still exfiltrate data via HTTP or submit
an adversarial form. HALO targets the gap between alignment and sandboxing by
intercepting injected content \textit{before} it enters the agent context and requiring
explicit approval for irreversible actions regardless of sandbox scope.

\subsection{Threat Model}

The adversary controls any text in external resources the agent reads (web pages,
documents, API responses) but cannot modify the agent's system prompt, the user's
initial task specification, or HALO itself. The model is grey-box: the adversary
understands that the target is an instruction-following LLM agent but does not
know specific prompt contents or HALO's scanning prompts. Goals include task
hijacking, data exfiltration, privilege escalation, and covert persistence (instructions
affecting future sessions).

Trust boundaries follow the principle of least privilege~\cite{saltzer1975protection}:
the user is fully trusted; the agent is conditionally trusted subject to the risk
policy; all external content---including HTTPS-sourced and authenticated-service
content---is treated as untrusted until scanned. HALO enforces these boundaries by
intercepting both the data-retrieval channel and the action-execution channel.


\section{Multi-Agent Framework Survey}

I evaluated seven frameworks against four criteria: \textit{controllability}
(can the user pause or redirect mid-task?), \textit{approval granularity} (can
approval requirements be tuned to action risk?), \textit{injection defense} (does
the system detect prompt injection in retrieved content?), and \textit{auditability}
(are actions logged for post-hoc review?). Ratings reflect documentation review and
source code inspection. The results are in Table~\ref{tab:comparison}.

AutoGen~\cite{wu2023autogen} exposes a configurable human-input frequency per
agent (always, never, or after a fixed number of turns) but does not tie that
frequency to any assessed risk; CrewAI~\cite{crewai2024} offers a comparable
flat toggle with the same lack of risk-proportional routing. MetaGPT~\cite{hong2023metagpt}
and ChatDev~\cite{qian2023chatdev} document human involvement only at the
start and end of a run, with no mid-pipeline pause described; MetaGPT achieves
High auditability through strict document schemas, ChatDev Medium through
readable but unstructured conversation logs. OpenHands~\cite{wang2024opendevin}
provides the richest tool access (terminal, filesystem, browser inside a
Docker sandbox) but no action-level approval or interruption in its default
configuration. Magentic-One~\cite{fourney2024magentic} directs specialized
sub-agents from a central orchestrator (38\% GAIA, 32.8\% WebArena) and
sandboxes execution in containers, but only recommends a human-approval gate
for high-stakes actions as future work, without implementing one.
Magentic-UI~\cite{fourney2025magenticui} is the closest prior work:
co-planning and co-tasking interfaces represent the state of the art in
human oversight, and its Action Guard already routes each action through one
of three preset tiers (always approve, never approve, or an LLM judge's
call). What it lacks is a continuously computed risk score, trust-adjusted
routing, and any content-level injection scanning.

Two findings stand out. No framework performs content-level scanning for injected
instructions---not even as an optional module. And approval granularity, at its best,
is a binary flag: Magentic-UI lets the user approve every action or none; most other
systems skip approval entirely. In no case is approval conditioned on a quantitative
estimate of what a specific action risks. HALO is a direct response to both absences.


\section{HALO: Human-Agent Loop Orchestrator}

\subsection{System Overview}

HALO is a human-in-the-loop multi-agent orchestration system. A Python
backend coordinates a WebSurfer, a Coder, a FileSurfer, and optional MCP tool
agents under a central Orchestrator, and exposes all of it through a
WebSocket-connected web frontend. This design addresses the two gaps the
survey turned up: no framework scans retrieved content for injected
instructions across every channel an agent reads from, and none calibrates
approval requirements to the risk of an individual action or to how
reliable the user-agent relationship has proven to be over time. An
\textit{Injection Gateway} scans content before it reaches any agent's
context, whether that content came from a web page, a file, code-execution
output, or an MCP tool result. A risk-scoring engine sits between each
agent's proposed action and its execution, routing the action to one of
three policies (auto-approve, notify-and-proceed, or require-explicit-
approval), and a Bayesian trust layer then adjusts how strict that routing
is for a given user and task category, based on their accumulated approval
history.

Figure~\ref{fig:architecture} shows where HALO fits; the agent roster is
drawn as a single ``Agent / Orchestrator'' box for clarity. The defining
architectural decision is that the \textit{Injection Gateway} is not a
preprocessing step bolted onto one edge of the pipeline: it is a mandatory
checkpoint every party in the system has to cross, in both directions,
every time, before reaching the trusted reasoning core. The caption walks
through the full round trip step by step. The pattern is the same as a
network firewall or an API gateway placed in front of a trusted service:
the agent itself never talks to the user or the external world directly.

HALO plugs into the agent framework without modifying the underlying model. Content
scanning and risk/trust scoring run as async Python coroutines invoked from each
agent's own message-handling loop, communicating with the frontend over a local
WebSocket channel. All LLM calls (injection detection, risk estimation, hijack
screening, plan generation) return structured JSON; on timeout or parse error the
corresponding layer marks itself unavailable and the system falls back to the
remaining layer(s) rather than silently permitting the action.

It is worth being direct about why all three of these live side by side
instead of collapsing into one. The Injection Gateway is only watching for
one thing: content that is trying to steer the agent somewhere it was not
told to go, a web page, a file, a tool result, or even the user's own
message if it is relaying someone else's instructions. It has no opinion
on whether an action is dangerous. That is the risk engine's job, and it
looks at the action on its own terms, regardless of where the instruction
came from. Trust sits on top of both and only decides how much friction a
given user still needs inside the category the risk engine already
picked; it cannot reach across categories and it cannot speak for either
of the other two.

Here is a case where treating these as interchangeable would break
something. Say a user has approved ten newsletter sign-ups in a row, so
the transactional bucket has drifted to a permissive policy, and then
types ``log into my bank and wire \$5{,}000 to this account.'' Nothing
about that sentence is an injection. There is no page, file, or relayed
instruction for the gateway to catch, so it stays quiet. The approval
streak does not help here either, because a bank transfer was never a
transactional-bucket task to begin with: the risk engine reads the
sentence itself, calls it destructive, and clamps the policy to
\textit{always-require} before trust gets a vote
(Section~\ref{sec:eval-gap3}, and the destructive floor described in
Section~\ref{sec:trust}). The wire-transfer tool is also hardcoded to
always require approval on its own, so even a broken classification step
would not let this through. Take the risk engine out of the picture and
this same plainly worded request sails through unopposed, since there was
nothing in it for the gateway to flag. Take trust out instead and nothing
gets more dangerous, but every routine action a user has already proven
safe keeps asking for the same approval forever, and a tool people stop
tolerating stops protecting anyone.

Two safety properties formalize the design goals. Let $D(c)$ denote the detection
decision for page $c$: $D(c) = I_{\text{rule}}(c) \vee I_{\text{llm}}(c)$
(OR-fusion: either layer firing is sufficient to quarantine).

\textbf{Definition 1} (\textit{Safety-calibrated policy}):
a policy $\pi: [0,1] \to \mathcal{P}$ is safety-calibrated if for all
$R \geq \tau_{\text{high}}$, $\pi(R) = \textit{always-require}$---no high-risk
action is auto-approved.

\textbf{Definition 2} (\textit{Injection-free context}):
the content set $\mathcal{C}$ delivered to the agent is injection-free if
$\forall c \in \mathcal{C},\; D(c) = \textit{false}$, i.e.,
$\neg I_{\text{rule}}(c) \wedge \neg I_{\text{llm}}(c)$;
pages for which $D(c) = \textit{true}$ are quarantined before entering the
agent's context window.

\subsection{Risk Scoring Engine}

Before any proposed action reaches the browser (opening a URL, submitting a
form, running a shell command, reading or writing a file), HALO scores it on
four dimensions. Action category gives a baseline: read, write, or execute,
where a read is generally less risky than an execution. Resource sensitivity
captures what is actually at stake, since accessing user data or system
files raises the score no matter which verb is used. Reversibility matters a
lot here too: a form submission that sends an external email cannot be
undone, and the score has to reflect that. The fourth dimension, task
deviation, checks whether the action is a plausible step toward what the
user actually asked for; an agent acting outside its declared scope earns
more scrutiny, not less.

Each dimension produces a component score in $[0, 1]$, and the aggregate is
the maximum of the two layers:
\begin{equation}
  R_{\text{fused}} = \max\!\left(R_{\text{rule}},\; R_{\text{llm}}\right)
  \label{eq:risk-fusion}
\end{equation}
$R_{\text{rule}}$ comes from the action-category and reversibility
heuristics. $R_{\text{llm}}$ is what a structured LLM query returns given
the full action context. Taking the maximum instead of an average is a
deliberately conservative choice: if either component flags an action as
dangerous, that assessment stands, because neither layer is reliable enough
on its own to overrule the other. An LLM running in a manipulated context
can rate a dangerous action as safe, which is exactly what an injection
attack is trying to achieve. A rule-based scanner, on the other hand, will
miss any injection that does not match its pattern list. Taking the maximum
of the two stops a compromised or incomplete component from quietly pulling
the alert level down.

The risk score then maps to three approval tiers. When $R_{\text{fused}} <
\tau_{\text{low}}$, the action auto-approves silently. When $\tau_{\text{low}}
\leq R_{\text{fused}} < \tau_{\text{high}}$, it triggers a notification the
user can dismiss or act on. When $R_{\text{fused}} \geq \tau_{\text{high}}$,
it halts execution until the user gives explicit approval.

\textbf{Threshold selection.}
Both thresholds were fixed before any test data were seen. A grid search over
$\tau_{\text{low}} \in \{0.20, 0.25, 0.30, 0.35\}$ and
$\tau_{\text{high}} \in \{0.65, 0.70, 0.75, 0.80\}$ minimizes the asymmetric loss:
\begin{equation}
  L = 5 \cdot e_{\text{under}} + e_{\text{over}}
  \label{eq:threshold-loss}
\end{equation}
where $e_{\text{under}}$ counts high-risk actions routed to auto-approve and
$e_{\text{over}}$ counts unnecessary confirmations. The 5:1 weight reflects the
asymmetric cost of a missed safety event versus an extra confirmation click.

\textbf{Threshold stability (LOOCV).}
On the 120-action evaluation set, all 16 valid grid pairs achieve $L = 0$ (zero
under-routing errors). This follows structurally from the risk-score separation:
$R_{\text{research}}=0.15$, $R_{\text{transactional}}=0.55$, $R_{\text{destructive}}=0.95$
leave large margins on both sides of any threshold in the valid ranges
$\tau_{\text{low}} \in (0.15, 0.55]$ and $\tau_{\text{high}} \in (0.55, 0.95]$.
A leave-one-out cross-validation over all 120 actions confirms 100\% selection
stability: removing any single action leaves the set of optimal pairs unchanged.
The pair $(0.30, 0.70)$ is adopted as the maximum-margin representative of the
valid region (furthest from both risk-score boundaries), and was locked in before
evaluating on test data.

\subsection{Bayesian Trust Calibration}
\label{sec:trust}

Fixed thresholds ignore demonstrated agent reliability. HALO maintains a Beta
distribution per risk tier:
\begin{equation}
  P(\theta \mid \alpha,\, \beta) = \frac{\theta^{\alpha-1}(1-\theta)^{\beta-1}}{B(\alpha,\beta)}
  \label{eq:beta}
\end{equation}
where $\theta$ encodes per-tier reliability and updates asymmetrically as:
\begin{equation}
  \alpha \leftarrow \alpha + 1.0\cdot\mathbf{1}[\text{approve}], \qquad
  \beta  \leftarrow \beta  + 1.5\cdot\mathbf{1}[\text{reject}] + 0.75\cdot\mathbf{1}[\text{correct}]
  \label{eq:trust-update}
\end{equation}
A single reject now costs $1.5\times$ what a single approve earns back, and
\textit{correct} (user modifies before allowing) keeps its original half-of-a-reject
ratio ($0.75$, versus $1.5$ for an outright reject). This asymmetry is a deliberate
mitigation, not an incidental default: because trust persists across sessions and
directly loosens future enforcement (see below), a habitually-approving user
(approval fatigue) or a task designed to farm easy approvals before a riskier one
could otherwise erode scrutiny faster than is safe under a symmetric update rule.
Under the symmetric weights ($+1/+1/+0.5$), ten consecutive approvals with
zero rejects were sufficient to flip the transactional tier from
\textit{auto-conservative} to \textit{auto-permissive}; under the asymmetric
weights a single reject anywhere in that streak costs $1.5$ approvals' worth of
progress to undo, so sustained bad behaviour is punished disproportionately to how
sustained good behaviour is rewarded.

Informative priors encode inherent tier danger before any observations: Research
$\text{Beta}(8,2)$ ($\hat{\theta}=0.80$), Transactional $\text{Beta}(5,5)$
($\hat{\theta}=0.50$), Destructive $\text{Beta}(2,8)$ ($\hat{\theta}=0.20$). This
handles the cold-start problem and keeps trust earned on research tasks from
affecting thresholds on destructive ones. Rather than adjusting $\tau_{\text{low}}$
continuously, the posterior mean $\hat{\theta} = \alpha/(\alpha+\beta)$ and its
confidence band (derived from $\sigma_n$, Eq.~\ref{eq:sigma}) select a discrete
policy: \textit{destructive} tasks are hard-floored to \textit{always} regardless of
$\hat{\theta}$; otherwise $\hat{\theta} \geq 0.75$ with non-low confidence selects
\textit{auto-permissive}; $\hat{\theta} \geq 0.40$ selects \textit{auto-conservative};
below that, \textit{always}. Section~\ref{sec:eval-gap3} reports live evidence of
this policy and its cross-run persistence under the new asymmetric weighting.

\textbf{Closed-loop enforcement and persistence.} In the current architecture the
trust-derived policy is not merely displayed: it is written back into the same live
\texttt{ApprovalGuard} instance the risk-scoring engine (Section~4.2) mutates,
immediately after Gap~1 classification, after every approve/reject decision, and
after an injection-block trust penalty is applied (Section~4.5). A per-user record
of $(\alpha,\beta)$ per tier is persisted to storage and reloaded at the start of
every subsequent run, so trust compounds across sessions rather than resetting to
the prior each time. This is gated by a single switch (default on) that, when
disabled, reverts trust to a display-only signal for ablation studies. The
destructive-tier floor is unaffected either way: no accumulated trust, in any run,
can loosen a destructive-classified task below full approval.

\textbf{Convergence guarantee.}
Let $n = n_a + n_r$ be the total number of feedback events. After $n_a$ approvals
and $n_r$ rejections from prior $\text{Beta}(\alpha_0,\beta_0)$,
the posterior parameters are $\alpha_n = \alpha_0 + n_a$, $\beta_n = \beta_0 + 1.5 n_r$,
and the posterior standard deviation is:
\begin{equation}
  \sigma_n = \sqrt{\frac{\alpha_n \beta_n}{(\alpha_n+\beta_n)^2(\alpha_n+\beta_n+1)}}
  \label{eq:sigma}
\end{equation}
By the AM-GM inequality, $\alpha_n \beta_n \leq \bigl((\alpha_n+\beta_n)/2\bigr)^2$,
so $\sigma_n^2 \leq 1/\bigl(4(\alpha_n+\beta_n+1)\bigr) = O(n^{-1})$ regardless of the
relative weighting of approvals versus rejections. This bound falls monotonically as
$\alpha_n+\beta_n$ grows, so $\sigma_n$ is trapped under a strictly falling ceiling and
$\sigma_n \to 0$ as $n \to \infty$; the asymmetric weighting changes the constant factor
and the approach direction (a given ratio of rejects now pulls $\hat\theta$ down faster
than the old weighting), not the asymptotic order. The bound, not $\sigma_n$ itself, is
what falls on every step: a single reject on an already-skewed posterior can pull
$\alpha_n,\beta_n$ back toward balance faster than the added mass shrinks the variance,
transiently \emph{raising} $\sigma_n$ before the long-run trend resumes---for the
research prior $\text{Beta}(8,2)$, $\sigma_0=0.1206$, one approve drops it to $0.1113$
but one reject instead raises it to $0.1301$. That is the correct behavior for a trust
model, not a defect: a rejection should read as more uncertainty, not just less trust.
Section~\ref{sec:eval-gap3} confirms the prior mean and standard deviation live in the
running system and shows they survive a connection reload under the current weights.

\subsection{Algorithm}

Algorithm~\ref{alg:halo} gives the formal pseudocode for the full decision
flow across both the injection and risk-routing branches.

\begin{algorithm}[H]
\caption{HALO Action Gate}
\label{alg:halo}
\footnotesize
\SetKwFunction{ScanActive}{ScanActive}
\SetKwFunction{PatternScan}{PatternScan}
\SetKwFunction{LLMScan}{LLMScan}
\SetKwFunction{Quarantine}{Quarantine}
\SetKwFunction{KeywordClassify}{KeywordClassify}
\SetKwFunction{LLMRisk}{LLMRisk}
\SetKwFunction{PolicyFromTrust}{PolicyFromTrust}
\SetKwFunction{HijackScreen}{HijackScreen}
\KwIn{User task $t$, proposed action $a$, retrieved content $\mathcal{C} = \{c_1,\ldots,c_n\}$
      (pages, files, code output, or MCP tool results)}
\KwOut{Decision $d \in \{\textsc{execute}, \textsc{block}\}$, updated trust $(\alpha, \beta)$}
\tcp{Step 1: task-text injection scan --- precedes Gap~1 classification}
\If{\ScanActive{}}{
  $I_{\text{rule}} \leftarrow$ \PatternScan{$t$}; $I_{\text{llm}} \leftarrow$ \LLMScan{$t$, \textsc{Task}} \tcp*{narrower prompt than Step 2}
  \If{$I_{\text{rule}} \vee I_{\text{llm}}$}{
    ask user \tcp*{telemetry report sent first either way}
    \If{user declines}{\Return{$\textsc{Block}$, $(\alpha,\beta)$} \tcp*{no plan this turn}}
  }
}
\tcp{Step 2: content scanning, one shared gateway call per source}
\ForEach{$c_i \in \mathcal{C}$}{
  \If{$c_i.\mathrm{id} \in \textsc{BlockedIds}$}{\Quarantine{$c_i$}; \textbf{continue}\;}
  $I_{\text{rule}} \leftarrow$ \PatternScan{$c_i$}; $I_{\text{llm}} \leftarrow$ \LLMScan{$c_i$, \textsc{Content}} \tcp*{skipped if hybrid layer off}
  \If{$I_{\text{rule}} \vee I_{\text{llm}}$}{
    ask user; \If{user declines}{\Quarantine{$c_i$}; $\textsc{BlockedIds} \mathrel{+}= c_i.\mathrm{id}$\;}
  }
}
\tcp{Step 3: risk scoring (rule + LLM), re-run on every new task message}
$R_{\text{rule}} \leftarrow$ \KeywordClassify{$t$}; $R_{\text{llm}} \leftarrow$ \LLMRisk{$t$} \tcp*{falls back to $R_{\text{rule}}$ on timeout}
$R_{\text{fused}} \leftarrow \max(R_{\text{rule}}, R_{\text{llm}})$; classify tier $\tau \in \{\text{research}, \text{transactional}, \text{destructive}\}$\;
\tcp{Step 4: trust-adjusted policy routing (destructive is immune)}
\uIf{$\tau = \textit{destructive}$}{
  policy $\leftarrow \textsc{Always}$ \tcp*{hard floor}
}\Else{
  policy $\leftarrow$ \PolicyFromTrust{$\hat\theta_\tau$, confidence$_\tau$} \tcp*{Eq.~\ref{eq:trust-update}--\ref{eq:sigma}}
}
\tcp{Step 5: action-hijack screening, independent of Step 4}
$H \leftarrow$ \HijackScreen{$t_{\text{instruction}}$, $a$}\;
\If{$H.\mathrm{suspected} \wedge H.\mathrm{confidence} \geq 0.6$}{
  policy $\leftarrow \textsc{Always}$ \tcp*{overrides Step 4 for this action}
}
\uIf{policy $= \textsc{Never}$ \textbf{or} baseline$(a) = \textsc{Never}$}{
  $d \leftarrow \textsc{Execute}$\;
}\uElseIf{baseline$(a) = \textsc{Always}$ \textbf{or} policy $= \textsc{Always}$}{
  halt; $d \leftarrow \textsc{Execute}$ iff approved\;
}\Else{
  live LLM judges $a$; $d \leftarrow \textsc{Execute}$ unless risky\;
}
\tcp{Step 6: asymmetric Bayesian trust update (per tier $\tau$)}
\lIf{user approves}{$\alpha_\tau \mathrel{+}= 1.0$}
\lIf{user rejects}{$\beta_\tau \mathrel{+}= 1.5$}
\lIf{user corrects}{$\beta_\tau \mathrel{+}= 0.75$}
\Return{$d$, updated $(\alpha_\tau, \beta_\tau)$}\;
\end{algorithm}

\subsection{Prompt Injection Detection}

Any content retrieved from an external source, a web page, a file,
code-execution output, or an MCP tool result, passes through the same
Injection Gateway before the requesting agent gets to read it. No agent
implements its own scanning logic separately. Two passes run in sequence
inside that gateway.

The rule-based pass checks the text against 26 lexical patterns split into
four categories. \textit{Social-engineering and instruction override} covers
9 patterns, things like ``ignore previous instructions,'' ``disregard your
instructions,'' or ``new task:''. \textit{Role-switching and persona
hijacking} covers 7, such as ``you are now,'' ``pretend you are,'' or
``roleplay as''. \textit{System-prompt manipulation} covers another 7,
including ``system prompt:'', ``override your'', and ``{[system]}''. And
\textit{exfiltration directives} cover the remaining 3: ``exfiltrate'',
``send all data to'', ``leak your''. The pattern set draws on Perez and
Ribeiro's injection taxonomy~\cite{perez2022ignore} and the OWASP LLM
Top~10~\cite{owasp2025llm}. Section~\ref{sec:eval-gap2} shows both the
pattern-only layer and the hybrid pattern-plus-semantic layer catching
deliberately injected content in the running system.

The LLM pass sends the retrieved text to a separate, sandboxed model call.
That call uses a fixed system prompt the content under inspection cannot
read or modify, so an injected instruction has no way to disable its own
detector. The model is asked one question: does this text look like it is
directing an AI agent, or is it just conveying information to a human
reader? A single configuration flag, YAML-only with no UI toggle, can turn
this pass off for ablation studies. The pattern pass has no such switch; it
always runs.

When either pass fires, the flagged content is quarantined and swapped out
for a visible placeholder in the agent's context, and the user gets an
alert. A silent telemetry report goes out first regardless of the outcome,
so the live oversight panel reflects scan activity even when the content
turns out to be clean. The approval policy tier itself can be changed from
the settings panel (Figure~\ref{fig:settings}), but the hybrid detection
layers are configuration-file flags meant for reproducible ablation studies,
and are not exposed in the settings UI on purpose.

\textbf{Action-hijack screening.} Content scanning asks whether
\textit{retrieved text} contains hidden instructions. A second, independent
check asks a different question about the agent's own \textit{next action}:
does this proposed action still look like a reasonable way to carry out the
current instruction, or does it look like the agent was steered into doing
something else by content it read earlier? This catches the case where a
novel or paraphrased injection slips past both scanning passes but still
visibly redirects the agent's behavior. Take a task asking for a weather
lookup where the agent's next proposed action is submitting a subscription
form that a page suggested along the way. This screen runs as a third
sandboxed LLM call, and when it fires above a confidence threshold it forces
an approval prompt no matter what the risk-and-trust policy in
Section~4.2--4.3 would otherwise have decided, including for an action that
a permissive, highly-trusted policy would normally wave through without a
second look.

\section{Experimental Evaluation}
\label{sec:eval}

\subsection{Executive Summary}

Rather than benchmark HALO offline against a fixed corpus, I tested the
running system directly, by hand. This meant the real backend, a real Docker
sandbox, a real browser, and a real hosted LLM (the University of Passau
InnKube cluster, running \texttt{qwen35-397b}). I ran 22 scenarios covering
all five executor surfaces: the web surfer, the coder agent, the file
surfer, the trust and feedback loop, and MCP tool integration. For each one
I sent a task through the actual chat UI myself and checked what the UI
showed afterward, whether that was a plan, an approval prompt, an injection
banner, or a trust panel value, rather than checking an internal function's
return value. A pass here means the feature worked the way a user would
actually see it, not just that a mocked unit test was satisfied.

Two of the 22, both action-hijack checks, were instead verified by calling
the underlying function directly with a deliberately mismatched instruction
and action: across every live attempt the model simply refused to take the
bait, which is the correct behavior but leaves no screenshot to point to.
Table~\ref{tab:tc-mcp} marks both accordingly. Testing also surfaced two real
bugs along the way, one in the file surfer and one in MCP tool-name
handling, both found and fixed as part of this evaluation and described in
Section~\ref{sec:eval-gap2}.

All 22 scenarios passed. Gap 1 routed a research task to
\textit{auto-permissive} and correctly forced a destructive task through a
per-action approval gate. Gap 2's pattern and semantic scanners caught
deliberately injected content across every surface they cover, pages, code
output, file content, and MCP tool results, while leaving ordinary requests
alone, and the action-hijack screen correctly forced approval when tested
directly against a mismatched instruction and action. Gap 3's trust panel
showed the exact value the math predicts ($\hat\theta=0.80$, $\sigma=0.12$
for the research tier's $\mathrm{Beta}(8,2)$ prior) and kept that value
after a session reload, confirming the \texttt{TrustProfile} persistence
path actually works across runs. Cooperative planning, per-action approval
and rejection, code execution and self-correction, file browsing, MCP
server registration, and MCP tool use were all exercised against the live
UI and each produced the expected result.

\subsection{Testing Methodology}

I tested every scenario by hand: opening a fresh session in the browser,
submitting a task or performing a UI action myself, and watching for a
specific, observable result before checking it against what that part of
the system is supposed to do. That result might be a plan rendering, an
approval button, an injection banner, or a trust-panel value. Where an LLM
response was slow to arrive, I gave it time rather than counting a scenario
as failed just because it had not finished yet. I also took a screenshot at
the decisive moment of every run, so a claim in this report can be checked
against a picture instead of taken on trust.

described above: 8 WebSurfer, 4 Coder, 4 FileSurfer, 2 Trust, and 4 MCP

on two of its three runs. On the third, no alert appeared inside the
observation window at all. The pattern itself is unlikely to be at fault,
since the same page and the same scanner caught it cleanly on both other
attempts; a timing race between the page finishing its render and the
scan reading the text is the more likely explanation. I am reporting that
miss instead of quietly re-running it away, because a single honest gap
is worth more here than a suspiciously perfect score.

From the confusion matrix:
\begin{align}
\text{Precision} &= \frac{TP}{TP+FP} = \frac{23}{23+0} = 1.00 \\
\text{Recall} &= \frac{TP}{TP+FN} = \frac{23}{23+1} = 0.958 \\
F_1 &= \frac{2 \cdot P \cdot R}{P+R} = \frac{2 \times 1.00 \times 0.958}{1.00+0.958} = 0.979
\end{align}

Precision of 1.00 means every alert the gateway raised in this corpus was
a genuine injection attempt, not a clean item wrongly flagged. Recall of
0.958 means one out of twenty-four injected trials slipped through
without triggering, and that same underlying page was still caught
correctly on its other two runs. None of this is an independent
benchmark. It is sixteen items I built, labeled, and ran myself, so these
numbers say how the gateway behaves on exactly that corpus, not how it
would hold up against every possible phrasing of an injection attempt in
the wild.

\subsection{Security and Robustness Evaluation}
\label{sec:eval-gap2}
\label{sec:eval-gap3}

\textbf{Gap 1 (Adaptive Action Guard).} A research question was classified
at risk 0.15 and routed to \texttt{auto-permissive} (Fig.~\ref{fig:qa-research});
a request to permanently delete browsing data was classified destructive,
scored 0.95, and routed to policy \textit{always}, forcing approval before
execution (Fig.~\ref{fig:qa-destructive-approval}).

\textbf{Gap 2, content scanning.} The pattern and semantic layers fired
independently of each other: pattern on a page with an explicit lexical
signature, gating the Block/Continue decision that followed
(Figs.~\ref{fig:qa-pattern-alert}--\ref{fig:qa-pattern-blocked}); semantic
on a page with no lexical pattern at all, detected through the LLM layer
alone (Fig.~\ref{fig:qa-semantic-alert}). A clean page produced no alert,
ordinary requests passed through uninterrupted
(Table~\ref{tab:tc-websurfer}, Table~\ref{tab:tc-coder}), and a task with an
embedded override attempt was still caught (Fig.~\ref{fig:qa-coder-inject}).
The same gateway covers file content and MCP tool results: an injected file
raised the alert attributed to the file itself, not the code that read it
(Fig.~\ref{fig:qa-filesurfer-inject}), and an injected MCP tool result
raised the alert attributed to the tool.

Two defects surfaced during this testing and were fixed. The file surfer
was not executing at all for most of the evaluation, silently replaced by
the coder agent, because it placed its system prompt after the conversation
history rather than before it --- an ordering the hosted model endpoint
rejects once any prior turn exists. Moving the prompt ahead of history, to
match the coder agent's existing convention, fixed it immediately.
Separately, the MCP tool-name escaping scheme handled hyphens only, so a
tool name with any other character (the reference ``everything'' server
ships one containing a colon) crashed schema conversion before the gateway
ever ran. Both are one-function fixes, now reflected in
Table~\ref{tab:tc-mcp}.

\textbf{Gap 2, action-level approval and hijack screening.} A proposed
action such as navigating to a URL or executing code is separately gated by
its own approval prompt (Figs.~\ref{fig:qa-action-approval},
\ref{fig:qa-coder-approval}); rejecting it stops execution
(Fig.~\ref{fig:qa-coder-reject}). The hijack screen asks a different
question --- not whether retrieved content is manipulative, but whether the
agent's own next action still matches its instruction --- and can force
approval even under a policy that would otherwise permit the action. It
never fired on its own, including against a page built to nudge the agent
toward an unrelated form submission: the model simply followed its
instruction, a correct outcome with no screenshot to show for it. Tested
directly instead, pairing a legitimate instruction against a deliberately
unrelated action (summarize a document vs.\ a shell command exfiltrating
system files, for the shared file-surfer/coder hook; check a weather
forecast vs.\ an unrelated arithmetic tool call, for the MCP hook), both
mismatches were correctly identified and both forced approval
(Table~\ref{tab:tc-mcp}, marked as verified this way rather than through the
browser).

\textbf{Gap 3 (Bayesian Trust Calibration).} A fresh session showed Trust
$=0.80$, $\sigma=0.12$, confidence ``medium,'' policy ``Permissive'' for
the research tier, exactly the $\mathrm{Beta}(8,2)$ prior's prediction
(Fig.~\ref{fig:qa-trust-panel}); the post-reload screenshot was
byte-for-byte identical, confirming \texttt{TrustProfile} persistence
survives a reconnect without corrupting the underlying Beta parameters.

\textbf{Robustness.} An invalid, unreachable URL produced an in-chat error
rather than crashing the session (Fig.~\ref{fig:qa-invalid-url}), and a
nonexistent file path was reported back gracefully by the file surfer.

\section{Discussion}

\subsection{Capability vs.\ Control}

The survey in Section~3 turns up a consistent pattern: the frameworks that
are best at completing tasks invest the least in safety. Part of that comes
down to how we measure things. Task success on GAIA or WebArena is easy to
score automatically, but whether a system would have been redirected
by an adversarial page takes deliberate adversarial test construction, and
none of the standard benchmarks bother. Part of it is an incentive problem
too: a safety layer that correctly blocks a dangerous action makes a
system's benchmark score go down, and no leaderboard gives credit for ``safe
and correct'' over plain ``correct.'' There is an architectural reason as
well. Capability-first frameworks tend to bolt safety on afterward, as a
wrapper around the output, and a wrapper like that cannot catch a compound
plan where every individual step looks fine but the sequence adds up to
harm.

The live evaluation in Section~\ref{sec:eval} shows that risk-proportional
approval and hybrid content scanning can both be built as a layer around an
existing agent system and checked end to end against the running
application, without touching the agent or the model underneath it. One
engineering problem is worth calling out: extending detection to a new
surface, here the user's own task text rather than only retrieved content,
means that surface needs its own threat model. Telling an agent to browse a
page or run code is normal operation, and a detector that reuses one prompt
across surfaces will confuse ``the user asked for an action'' with ``an
attacker is redirecting the agent.'' Section~\ref{sec:eval} shows the
task-text scan making exactly that distinction, on both ordinary and
adversarial requests, which is what keeps the gateway useful without
obstructing the agents it protects. So the fact that none of the seven
surveyed frameworks implement risk-proportional approval or hybrid content
scanning is not fully explained by technical difficulty: getting the
false-positive and false-negative balance right on every surface a system
touches is real, ongoing engineering work, and this evaluation's live
results show that it can be done.

\subsection{Limitations and Open Problems}

Several limitations deserve direct acknowledgment. The 22-scenario pass is a
live, black-box functional and security assessment, not a statistical
detection-accuracy benchmark, and it shows that each mechanism works
correctly end to end on the traces I exercised without putting a precision
or recall number on any of them. The separate ground-truth pass in
Section~\ref{sec:ground-truth} does produce one, Precision 1.00, Recall
0.958, F1 0.979 for the Injection Gateway, but that corpus is sixteen items
I built and labeled myself, not an independently curated benchmark. It
demonstrates that the metric is measurable and shows where the system
currently sits on it; it is not a figure that belongs next to a published
detection-accuracy leaderboard. All testing ran against a single hosted
LLM endpoint (\texttt{qwen35-397b}), so the latency numbers in
Table~\ref{tab:qa-latency} belong to that model and that endpoint and might
not carry over to a different provider. Each scenario also exercises one
representative task per capability instead of a wide spread of phrasings. A
larger battery covering more varied task language would give more confidence
that the boundary this evaluation found for task-text scanning, ordinary
action requests pass through, adversarial or relayed instructions get
caught, actually holds at scale.

On a broader point about the architecture: human oversight tends to work
better when it is built into the agent's planning process instead of being
tacked on afterward. The co-planning interface is a step in that direction,
but designing plan representations that people can actually review under
real time pressure is still an open problem~\cite{amershi2019guidelines}.
There is also a privacy angle worth stating plainly: HALO sends every piece
of retrieved web content, file content, code output, and the user's own
task text to a second LLM for scanning. Any production deployment of this
needs explicit user consent, a clear data-retention policy, and, where it is
practical, an on-device or on-premises model so sensitive content never
leaves the user's own infrastructure.

\section{Conclusion}

None of the seven multi-agent frameworks surveyed here implement
content-level injection scanning or per-action risk-proportional approval.
HALO's Adaptive Oversight Framework shows that both are achievable as a
layer around an existing agent system, and the live, 22-scenario evaluation
against the running application, not an offline benchmark, backs that up:
all three layers, and both action-hijack checks verified by direct
invocation, behaved correctly end to end, as detailed in Section~5.

What this cannot answer is how people actually respond to it: whether seeing
a risk score changes how a user decides, and whether adjusting the Bayesian
threshold leads to better outcomes in real sessions, are open questions that
need user studies I have not run. The ground-truth pass does put a precision
and recall number on the Injection Gateway, 1.00 and 0.958 over 48 trials,
but the corpus behind it is sixteen items I built and labeled myself. It
shows the metric can be measured cleanly. It does not settle how the system
would fare against a larger, independently-built adversarial corpus. And on
the benchmark side, there is little incentive to build
injection defenses as long as leaderboards only measure task completion and
ignore what a system refuses to do under pressure. That is the deeper
problem, and it has nothing to do with what is technically possible.
